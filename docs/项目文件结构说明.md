# 校园失物招领系统：项目文件结构说明

配套契约：[共同字段与接口约定](共同字段与接口约定.md)。

### 2.1 每类文件写什么

| 文件 | 应负责的内容 | 以发布招领信息为例 |
|---|---|---|
| `urls.py` | URL 与接口入口的对应关系 | `/posts` 对应创建/列表接口 |
| `views.py` | 接收请求、执行认证/校验、调用业务、组织响应 | 得到当前用户和已校验数据，调用创建函数 |
| `serializers.py` | 请求字段校验及返回字段的明确映射 | 校验标题长度；生成 `PostDetail` |
| `services.py` | 会改变业务数据的规则和操作 | 创建信息、绑定图片、保存数据 |
| `selectors.py` | 读取、筛选、分页所需的查询 | 查询公开招领列表 |
| `models.py` | 数据表字段、关联、唯一性约束、状态枚举 | 定义 `Post.publisher` 和 `Post.status` |
| `permissions.py` | 当前用户能否访问/操作资源 | 判断是否本人信息 |
| `migrations/` | 可追踪的数据库结构变更 | 增加字段、关联或索引 |
| `tests/` | 验证本模块的主要业务规则 | 非本人不能修改、非法图片不能上传 |

DRF 的序列化器用于数据转换与校验；这里的 `services.py`、`selectors.py` 是团队为明确职责采用的组织方式，不是 Django 强制要求的文件。[DRF 序列化器文档](https://www.django-rest-framework.org/api-guide/serializers/)

小型模块先各用一个 `views.py`、`serializers.py`、`services.py`。只有某个文件明显变大时才拆成包，不必一开始为每个接口新建一层目录，也不额外增加 Repository/DAO 层去重复包装简单 ORM 操作。

### 2.2 共享字典为何单独放 `catalog`

校园身份绑定需要引用校区，物品信息需要引用校区、类别和地点，匹配也需要这些数据。独立放置后，模型依赖关系为：

```text
catalog.models                    # 不依赖三个业务模块
       ↑
users.models                      # CampusBinding 引用 catalog.Campus
       ↑
posts.models                      # 引用 users.User 和 catalog 中的字典
       ↑
claims.models                     # 引用 users.User 和 posts.Post
```

B 负责维护 `catalog`，A 在初始化流程中安排先创建字典，再生成演示账号和校园身份。这样不需要把 `CampusBinding` 的基础身份依赖放进物品信息模块，也避免用户模型和物品模型互相依赖。

`AuthSession`、`DemoIdentity` 是为了实现已有令牌和演示绑定约定所需的内部模型建议，不增加公开接口或公开字段。

### 2.3 Django 用户模型需要先确定

建议从项目开始就使用 `users.User`，继承 Django 的 `AbstractUser`，再添加昵称、资料等业务字段。在第一次生成迁移、第一次执行迁移前设置 `AUTH_USER_MODEL = "users.User"`。其他模型引用用户时使用 `settings.AUTH_USER_MODEL`。这一先后顺序符合 Django 自定义用户模型的要求。[Django 用户模型文档](https://docs.djangoproject.com/en/stable/topics/auth/customizing/#using-a-custom-user-model-when-starting-a-project)

字段契约描述的是 API 和逻辑模型，不要求机械复制 Django 内部字段：例如哈希密码使用 Django 提供的密码设置/校验能力，不另写明文密码列；API 中的 `created_at` 可以明确映射注册时间。`is_campus_verified` 等按既有契约计算，不能让普通资料修改接口直接赋值。

`users/authentication.py` 负责接入 DRF 认证扩展点，并按现有契约实现 Bearer、24 小时到期、注销失效和 401 响应；采用某个框架认证类时，仍要核对这些行为，不能只因登录成功就算完成。[DRF 认证文档](https://www.django-rest-framework.org/api-guide/authentication/)

## 3. 跨模块流程放在哪里

**单模块规则放各自的 `services.py`；跨模块事务放 `workflows`。**

例如“同意认领”这一个操作，同时影响目标申请、竞争申请和物品状态，由 C 编写 `workflows/claim_workflow.py` 调用 B、C 的底层业务函数。这里保留了原接口文档中“C 发起，B 提供信息状态变更能力”的责任划分。

```text
claims/views.py
       ↓
workflows/claim_workflow.py        # C：统一权限、锁定顺序和事务范围
       ├── claims/services.py     # C：接受申请、关闭竞争申请
       └── posts/services.py      # B：把信息切换为交接中或已完成
```

撤回信息则由 B 的 HTTP 入口调用另一条流程：

```text
posts/views.py
       ↓
workflows/post_workflow.py         # B：统一权限、锁定顺序和事务范围
       ├── posts/services.py      # B：撤回信息
       └── claims/services.py     # C：关闭该信息的待审核申请
```

实现约定：

- `workflows` 调用业务模块，底层 `services.py` 不再反向导入 `workflows`，两个业务模块的写入服务也不互相循环调用。
- 完成认领、同意申请、撤回等操作在同一个 `transaction.atomic()` 事务内修改相关记录，任一步失败一起回滚；锁定顺序沿用接口约定。[Django 事务文档](https://docs.djangoproject.com/en/stable/topics/db/transactions/)
- 并发敏感的创建申请、取消、拒绝也由 `claim_workflow.py` 统一锁定和检查状态，底层服务只接收已经锁定的对象并实施本模块变更。
- 图片写入、普通编辑等不涉及认领状态变更的操作，由 B 的业务服务负责自己的事务。
- `claims/messages.py` 发消息时也需在事务中按“先信息、后申请”的顺序确认允许沟通，再写消息，避免与撤回/完成流程产生竞态。
- 前端只请求一次业务接口，不分别请求两次去凑成“申请完成＋物品完成”。
- 第一版不使用信号去隐藏这些跨模块状态变化，调用链保持可读，方便联调和答辩。

### 4.1 前端文件职责

| 文件/目录 | 规则 |
|---|---|
| `pages/` | 一个完整页面，组织组件和用户操作 |
| `components/` | 本模块内复用的表单、列表项、沟通区等 |
| `api.js` | 该模块全部 HTTP 调用；页面不要重复拼接口路径 |
| `routes.js` | 该模块拥有的页面地址和路由元数据 |
| `shared/http.js` | 统一处理请求、响应包装和错误；上传时不强行设置 JSON Content-Type |
| `shared/session.js` | 仅维护内存状态和读写方法，不导入业务模块或发请求 |
| `constants.js` | 前端展示文案和选项，不替代后端的权限及状态检查 |
| `composables/` | 跨组件复用的 Vue 逻辑；用到时再添加，不预设大量空文件 |

`users/api.js` 调用 `shared/http.js`，登录成功后由用户模块更新 `shared/session.js`；`http.js` 可以读取内存令牌，但不能反向导入 `users/api.js`，避免循环依赖。退出或收到 401 时清理会话，涉及跳转的动作交给页面/路由协调。

分类、地点的值来自字典接口，不能各模块自己写一套编号。`PostImageUploader.vue` 的私有预览通过带令牌的图片请求获得 Blob 地址，并在组件卸载时释放；用户上传文件不进入 `frontend/public/`。

### 4.2 页面职责与建议前端路由

以下是浏览器页面路由，不是 `/api/v1` 后端接口。

| 页面路由 | 所有者 | 对应页面 |
|---|---|---|
| `/login`、`/register` | A | 登录、注册 |
| `/me/profile`、`/me/campus-binding` | A | 个人资料、校园身份 |
| `/posts` | B | 公开列表、搜索筛选 |
| `/posts/new` | B | 发布失物/招领信息 |
| `/posts/:id`、`/posts/:id/edit` | B | 详情、编辑 |
| `/me/posts` | B | 我的发布，挂在个人中心框架下 |
| `/claims/new?post_id=...` | C | 创建认领申请 |
| `/me/claims?role=applicant` | C | 我申请的 |
| `/me/claims?role=publisher` | C | 我收到的申请 |
| `/claims/:id` | C | 申请详情、沟通、审核、交接 |
| `/posts/:id/matches` | C | 当前信息的匹配结果 |

`AccountLayout.vue` 由 A 提供菜单和子路由展示位置；A 不重写 B 的 `MyPostsPage.vue` 或 C 的 `ClaimListPage.vue`。三个模块的 `routes.js` 分别导出主页面路由和个人中心子路由，由总路由统一挂载。

在 B 的详情页点击“申请认领”，跳转到 C 的申请页并传入 `post_id`；点击“查找匹配”跳到 C 的匹配页。C 从接口重新读取并校验信息，不能相信 URL 参数代表操作权限。匹配页如要复用信息卡片，通过 B 的 `posts/index.js` 导出使用，由 B 维护组件实现。

## 5. HTTP 接口对应哪个后端模块

**目录归属由业务决定，不能只看 URL 的第一个单词。**

| 后端路径（省略 `/api/v1`） | Django 路由文件 | 说明 |
|---|---|---|
| `/auth/...`、`/users/me`、`/users/me/campus-binding` | `users/urls.py` | A 的身份和个人资料 |
| `/meta/...` | `catalog/urls.py` | B 维护的公共字典 |
| `/posts`、`/posts/{id}`、编辑/撤回/恢复/找回操作 | `posts/urls.py` | B 的信息业务 |
| `/post-images`、`/post-images/{id}/content` | `posts/urls.py` | B 的上传及受控图片读取 |
| `/users/me/posts` | `posts/urls.py` | “我的发布”仍属于 B |
| `/claims/...`、`/users/me/claims` | `claims/urls.py` | C 的认领及消息业务 |
| `/posts/{id}/matches` | `claims/urls.py` | 匹配属于 C |

总路由只负责汇总，各模块保留自己的完整相对路径。例如 `config/urls.py` 可以采用下面的示意结构：

```python
from django.urls import include, path

urlpatterns = [
    path("api/v1/", include("users.urls")),
    path("api/v1/", include("catalog.urls")),
    path("api/v1/", include("posts.urls")),
    path("api/v1/", include("claims.urls")),
]
```

于是 `posts/urls.py` 可声明 `posts`、`posts/<str:post_id>`、`users/me/posts` 等路径，`claims/urls.py` 声明 `claims` 和 `posts/<str:post_id>/matches` 等路径。完整模式不重复，保持原契约“不带结尾斜杠”的规则。Django 的 `include()` 用于把 URL 分发到各模块；上述分组是本项目的设计选择。[Django URL 文档](https://docs.djangoproject.com/en/stable/topics/http/urls/)

第一版可用明确的 `path()` 和 DRF APIView 实现接口，暂不依赖自动路由生成改变既有路径。一个 URL 同时有 GET/POST 时，由对应接口类区分方法。

## 6. 三个人实际维护哪些文件

| 成员 | 常规负责目录 | 指定维护的共享文件 | 合作部分 |
|---|---|---|---|
| A | `backend/users/`、`frontend/src/modules/users/` | `backend/config/`、`backend/common/`、`frontend/src/shared/http.js`、`session.js`、总路由及布局的初始骨架 | 维护初始化入口，和 B/C 确认公共契约 |
| B | `backend/posts/`、`backend/catalog/`、`frontend/src/modules/posts/` | `frontend/src/shared/catalogApi.js`、通用分页/空态组件 | `workflows/post_workflow.py` 主写；配合 C 验证状态更新 |
| C | `backend/claims/`、`frontend/src/modules/claims/` | `workflows/claim_workflow.py` 主写 | 与 B 联调事务流程；组织端到端验收用例 |

这张表指定主要维护者，不表示其他人不能修改公共代码。公共骨架只初始化一次，后续修改提前同步；每个人仍要为自己的前后端和业务规则编写测试。A 的公共骨架是初期额外工作，三人应在初始化阶段共同核对，避免全部联调任务都压给 A。

`requirements.txt`、`package.json` 和前端锁文件属于共享文件；依赖变更先说明用途再合并，三个人不要分别选择不同版本。数据库迁移由相应模型的负责人生成、提交，其他人通过迁移同步表结构。

## 7. 建立工程时的顺序

1. **建立公共骨架**：根目录、Django 配置、Vue 主入口、响应格式、HTTP 封装和基础路由；三人共同确认。
2. **先建立基础模型**：`catalog` 字典与自定义 `users.User`，再建立校园绑定、信息和认领模型；核对迁移依赖后再运行数据库迁移。
3. **按业务并行开发**：A 做登录/绑定，B 做发布/浏览，C 做认领/沟通。这里指三位组员各自开发，不代表创建三个独立服务。
4. **集中联调两个流程文件**：先打通认领完成，再覆盖撤回、取消和竞争申请；分别检查信息状态与申请状态。
5. **同步文档与验收记录**：接口规则改动更新共同契约，已验证结果写入验收文档，个人成果记录到各自报告。

建骨架时只创建当前开发需要的文件；树中的测试文件、页面组件、管理命令随功能实现逐步增加。暂不为尚未开发的后台管理、聊天附件、消息队列等功能占目录。

## 8. 仓库中应保存与应忽略的内容

应保存：源代码、依赖清单和锁文件、迁移文件、配置示例、无敏感数据的初始化逻辑、文档和测试。

应忽略：`.env`、`.venv/`、`__pycache__/`、`node_modules/`、`dist/`、`backend/media/`、日志、数据库文件和备份。`.env.example` 应提交，但只包含变量名、非敏感默认值和占位说明。

上传图片留在后端私有存储位置，由有权限检查的接口读取；不能为了开发方便给整个 `media` 目录加永久公开访问，从而绕过既定的撤回规则。
