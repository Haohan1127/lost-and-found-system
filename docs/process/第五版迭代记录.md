# 第五版迭代记录（认领“多次同意”防护，2026-11-12）

## 1. 反馈问题

测试同学反馈：

1. 同一物品好像可以多次同意：同意一条申请后，其他申请仍保留，担心还能再同意；
2. 申请一次后再次申请，会出现“已有有效认领申请”。

## 2. 问题定位

| 现象 | 结论 |
|---|---|
| 同一物品能否多次同意 | **不能**。同意一条时，C 的 `accept_claim` 会把该物品其余 `pending` 申请置为 `closed`（`close_reason=another_claim_accepted`），并把物品改为 `in_handover`；数据库还有“同一物品最多一条 accepted”的唯一约束。再次同意返回 409 |
| 其他申请为什么还“保留” | 关闭的申请没有删除，作为历史记录保留（便于双方回看和审计），所以列表仍能看到，但状态是“已关闭”，不再有同意按钮 |
| 为什么仍能点到同意 | 旧页面/旧数据可能残留待处理状态；原前端只按申请状态判断按钮，没有同时检查物品是否已进入交接。现在前端补了物品状态判断，后端文案也明确了原因 |
| “已有有效认领申请” | 同一申请人对同一物品只能有一条 `pending/accepted` 申请；不同物品可分别申请。这是既有契约，不是本次新限制 |

## 3. 本版改动

### 3.1 后端（C 认领流程）

- `backend/workflows/claim_workflow.py`
  - 同意时区分两种冲突并给出明确文案：
    - 申请已结束 → “该申请已结束，不能重复同意”；
    - 物品已被其他申请同意/已进入交接 → “该物品已有其他申请被同意或已进入交接，不能再次同意”。
  - 保持同意时自动关闭其余 `pending` 申请的事务逻辑。
- `backend/tests/test_handover_flow.py`
  - 新增 3 条申请场景：同意第一条后，其余两条全部 `closed`，无残留 `pending`，`accepted` 仅一条；再次同意被 409 拒绝。

### 3.2 前端（发布者/申请者视图）

- `frontend/src/modules/claims/constants.js`
  - `availableActions` 增加物品状态判断：物品已不是 `open` 时，发布者不再看到“同意/拒绝”按钮，避免旧页面误操作；申请者仍可撤回自己的 pending 申请。
- `frontend/src/modules/claims/pages/ClaimDetailPage.vue`
  - 同意成功后提示：“已同意该申请，其他待处理申请已自动关闭，物品进入交接中。”
  - 对“物品已交接但申请仍 pending”的异常视图，显示明确说明并隐藏审核按钮。
- `frontend/src/modules/claims/pages/ClaimListPage.vue`
  - 列表顶部说明：同一物品只允许一条申请被同意，其他申请自动关闭并保留记录；
  - 已关闭的申请显示关闭原因（如“发布者选择了其他申请”），不再让人误以为仍待处理。

## 4. 验证

| 检查 | 结果 |
|---|---|
| 后端全量（`tests users.tests`） | **112/112 通过**（含 C 的 13 项交接流程测试） |
| 前端单元测试 | **56/56 通过**（新增物品已交接时发布者无审核按钮的用例） |
| Vite 生产构建 | 通过 |
| 接口手工复现 | 对同一物品创建 2 条申请 → 同意第一条：第二条变 `closed`，原因为 `another_claim_accepted`；再次同意第二条返回 409；测试数据已清理 |

## 5. 结论

- “其他申请保留”是**历史记录**，不是仍可同意；真正可同意的只有 `pending` 且物品仍 `open` 的申请。
- “同一物品可多次同意”在本次迭代前也不会成功（数据库和事务都会拦住），但旧前端没有把原因和状态说清楚；本版把按钮、提示、关闭原因和错误文案一起补齐。
- “同一物品一人只能一条有效申请”保持不变；如需改为允许同一人多次提交，属于契约变更，不建议在演示版打开。
