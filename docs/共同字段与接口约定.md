# 校园失物招领系统：共同字段与接口约定

版本：v0.3（v0.2 + 2026-11-09 修订：发布权限按身份分路径——失物登录即可，招领需校园认证；校外人员发布的失物由 C 提示交接地点）  
日期：2026-10-07  
适用范围：用户管理、信息发布和浏览、失物认领三个子系统。

本文是三人共同开发的建议契约，不代表接口已经实现或经过测试。字段名、状态值和路径可直接用于前后端联调；正式开发前由三人共同确认。本文不绑定编程语言、前端框架或数据库。

> **v0.1.1 批注（2026-11-08，B 成员整理）**：保留 v0.1 契约主体，不改任何字段、路径和状态语义；新增内容一律用 **【B 注记】** 标注，只写实现与联调层面的提醒。B 负责的部分是 3.4 字典、3.5 信息、3.6 图片、第 5 节接口；第 3.7～3.9 的认领、消息、共用结构按需查阅，不实现。

## 1. 分工和第一版范围

| 成员 | 子系统 | 至少两个独立功能模块 | 数据及接口负责人 |
|---|---|---|---|
| A | 用户管理 | 注册登录；校园身份绑定；个人资料管理 | 用户、登录会话、校园身份绑定 |
| B | 信息发布和浏览 | 信息发布与维护；列表详情浏览；搜索筛选 | 失物/招领信息、图片、分类地点字典 |
| C | 失物认领 | 认领流程；双方站内沟通；规则匹配 | 认领申请、沟通消息、匹配结果计算 |

共同遵守以下边界：

- 每人完成自己模块的页面、接口、业务逻辑、数据操作、测试及文档。
- 个人中心由 A 提供页面框架和导航；“我的发布”的页面与列表由 A 直接查询 B 的 `Post` 表（按 `publisher_id` 过滤，同库直查），B 不再单独提供“我的发布”列表接口，`GET /posts` 只服务公开浏览；“我的认领/收到的申请”的列表及接口由 C 负责。
- A 提供登录身份，B、C 仍必须在后端校验各自业务的操作权限。
- B 维护信息状态的变更规则，C 在认领流程中调用 B 的内部业务函数，不能由浏览器直接指定信息已完成。
- 第四个系统管理子系统暂不开发；不包含管理员审核、争议裁决、备份管理等业务。
- 图片内容的责任提示由 B 在发布页提供固定文案；图片下架、举报受理与争议处置属于系统管理子系统的“发布信息管理”，B 不实现，边界表注明由谁做。

### 1.1 第一版的具体取舍

1. 登录后可以浏览全部公开信息；未登录也可以浏览、搜索公开信息。
2. 发布失物信息（`lost`）只需登录；发布招领信息（`found`）需要完成校园身份绑定，未绑定时返回 403 `IDENTITY_REQUIRED`，前端提示「非校园用户不能发布招领，请将物品送至失物招领处」并给出地址与联系方式。因为尚未接入学校认证服务，第一版采用**预置测试校园身份的演示绑定**；页面必须显示“演示认证”，不声称真实校园认证。
3. 失物信息用 `lost` 表示，招领信息用 `found` 表示，统一存储、统一发布接口。
4. **认领申请可以针对 `found` 招领信息，也可以针对 `lost` 寻物信息发起**：针对 `found` 时，申请者是自称失主的用户，审核者是招领发布者；针对 `lost` 时，申请者是捡到物品的人，审核者是寻物发布者（失主）。
5. 认领流程统一：无论目标是 `lost` 还是 `found`，都走“申请 → 审核者同意 → 交接中 → 双方确认 → 完成”；交接完成后信息进入 `completed`。
6. 沟通采用认领申请内的站内文字消息；每条申请就是一个会话，不开放任意用户私聊。
7. 匹配先使用分类、地点、时间、关键词规则，匹配结果只供参考，不自动发起申请或完成交接。

## 2. 全局接口格式

### 2.1 路径、命名及请求方式

| 项目 | 统一约定 |
|---|---|
| 接口前缀 | `/api/v1` |
| 路径 | 使用复数资源名，不带结尾 `/`，例如 `/api/v1/posts` |
| JSON 字段 | 使用 `snake_case`，例如 `publisher_id` |
| JSON 请求 | `Content-Type: application/json` |
| 图片上传 | `multipart/form-data`，由客户端库生成 boundary |
| ID | 对外统一使用字符串，例如 `"1001"`；客户端不计算、不猜测 ID |
| 时间 | ISO 8601 带时区；响应统一 UTC，例如 `2026-10-07T02:00:00Z`；页面按北京时间显示 |
| 布尔值 | JSON 的 `true` / `false` |
| 枚举 | 固定英文小写值；中文文案在前端映射 |
| 空值 | 可空字段明确返回 `null`；空数组返回 `[]` |
| 创建/操作 | `POST`；创建资源一般返回 HTTP 201，登录、状态操作等返回 HTTP 200 |
| 修改 | `PATCH` 只提交允许修改的字段；缺省字段保留原值 |
| 删除资源 | 第一版不提供信息/认领的物理删除接口，使用撤回或取消 |

字符串长度按字符数计算，标题、描述、昵称、消息等普通文本的前后空白由服务端去除；密码、令牌和绑定码按原值校验，不自动裁剪或改变大小写。描述、消息等都是纯文本，展示时按文本处理。请求中出现未知字段或只读字段，统一返回 `400 VALIDATION_ERROR`，避免客户端误以为修改成功。

### 2.2 登录身份

登录成功后返回 `access_token`，后续请求携带：

```http
Authorization: Bearer <access_token>
```

- 第一版建议采用服务端可撤销的随机会话令牌，有效期 24 小时，不增加刷新令牌接口。
- 服务端保存令牌摘要，不保存可直接使用的原始令牌；每次登录建立独立会话。
- 退出登录只撤销当前令牌。过期或撤销后的令牌返回 `401 UNAUTHENTICATED`。
- 前端第一版将令牌保存在内存中，刷新页面后重新登录；若调整登录保持方式，由 A 统一更新本约定。
- `user_id`、`publisher_id`、`applicant_id`、`sender_id` 均由后端从当前登录身份生成，不能相信客户端提交的身份字段。
- 公开接口不携带令牌即可访问；如果携带无效令牌，也返回 401，客户端清理令牌后可以重新匿名请求。

### 2.3 成功响应

统一使用 `code`、`message`、`data` 三个字段：

```json
{
  "code": "OK",
  "message": "操作成功",
  "data": {
    "id": "1001"
  }
}
```

无返回对象的操作使用 `data: null`。前端依赖 HTTP 状态和 `code`，不解析中文 `message` 判断业务结果。

### 2.4 失败响应

```json
{
  "code": "VALIDATION_ERROR",
  "message": "请检查填写内容",
  "data": null,
  "errors": {
    "title": ["标题不能为空"],
    "occurred_at": ["时间不能晚于当前时间"]
  }
}
```

`errors` 始终是对象，没有字段错误时返回 `{}`。

| HTTP 状态 | `code` | 含义 |
|---|---|---|
| 400 | `VALIDATION_ERROR` | 字段、查询参数或请求格式不正确 |
| 401 | `UNAUTHENTICATED` | 未登录、登录凭证错误或令牌失效 |
| 403 | `FORBIDDEN` | 已登录但无操作权限 |
| 403 | `IDENTITY_REQUIRED` | 该操作需要先完成校园身份绑定 |
| 404 | `NOT_FOUND` | 资源不存在，或按可见性规则不应暴露 |
| 409 | `STATE_CONFLICT` | 当前状态不允许操作 |
| 409 | `DUPLICATE_RESOURCE` | 账号、校园身份或有效认领申请重复 |
| 413 | `FILE_TOO_LARGE` | 图片超过限制 |
| 415 | `UNSUPPORTED_MEDIA_TYPE` | 请求内容类型或图片格式不支持 |
| 429 | `RATE_LIMITED` | 请求过于频繁；同时返回 `Retry-After` 响应头 |
| 500 | `INTERNAL_ERROR` | 服务端错误；不向客户端返回堆栈、SQL 或内部路径 |

对公开可见但无权修改的信息返回 403；对非参与者访问认领、消息，或非本人访问已撤回信息，统一返回 404。

### 2.5 分页、查询和排序

普通列表默认 `page=1&page_size=20`，`page_size` 范围 1～100。超出范围、非法数字、未知枚举返回 400。查询字符串中的布尔值使用 `true` / `false`。

```json
{
  "code": "OK",
  "message": "查询成功",
  "data": {
    "items": [],
    "page": 1,
    "page_size": 20,
    "total": 0,
    "total_pages": 0
  }
}
```

- 总数为 0 时，`total_pages=0`；页码超过最后一页返回空列表，不返回 404。
- 普通列表默认按 `created_at DESC, id DESC` 排序，保证相同时间时顺序稳定。
- 支持的排序参数由具体接口列出，不接受任意数据库字段。
- 匹配和消息增量读取有自己的返回结构，不强行套普通分页。

## 3. 共同数据字典

这里的字段表是逻辑模型；实现时可以拆表或添加必要索引，但不要擅自修改对外字段含义。

### 3.1 通用字段

| 字段 | API 类型 | 含义 | 写入方 |
|---|---|---|---|
| `id` | string | 唯一标识 | 服务端 |
| `created_at` | datetime | 创建时间 | 服务端 |
| `updated_at` | datetime | 最近更新时间 | 服务端 |

所有业务关联使用 ID。用户名、昵称、标题可能变化，不能用作外键。

### 3.2 用户 `User`（A）

| 字段 | API 类型 | 约束/说明 | 可见范围 |
|---|---|---|---|
| `id` | string | 服务端生成 | 本人；公开用户摘要 |
| `username` | string | 4～32 位字母、数字、下划线；统一存小写；唯一；注册后不修改 | 本人 |
| `password_hash` | 不返回 | 数据库内部字段；密码使用成熟密码哈希实现，不保存明文 | 仅服务端 |
| `nickname` | string | 1～30 字 | 本人；公开用户摘要 |
| `bio` | string | 0～200 字，默认空字符串 | 仅本人，第一版不公开个人主页 |
| `is_campus_verified` | boolean | 由身份绑定结果计算，只读 | 本人；公开用户摘要 |
| `verification_mode` | enum/null | 第一版为 `demo` 或 `null` | 本人；公开用户摘要 |
| `created_at` | datetime | 注册时间 | 仅本人 |
| `updated_at` | datetime | 最近修改时间 | 仅本人 |

密码只在注册/登录请求中出现，长度 8～64 字符；响应中不得出现密码或密码哈希。

`UserSummary` 是其他子系统唯一使用的公开用户结构：

```json
{
  "id": "1001",
  "nickname": "小林",
  "is_campus_verified": true,
  "verification_mode": "demo"
}
```

不在公开信息或匹配结果中返回账号、校园卡号、真实姓名、手机号。第一版通过认领会话联系，不要求发布联系电话。

### 3.3 校园身份绑定 `CampusBinding`（A）

| 字段 | 类型 | 约束/说明 |
|---|---|---|
| `id` | string | 绑定记录 ID，仅服务端使用 |
| `user_id` | string | 一个用户最多一条绑定，唯一 |
| `campus_id` | string | 关联校园字典 |
| `student_no` | string | 6～20 位字母或数字；与 `campus_id` 联合唯一；仅服务端校验使用 |
| `verification_mode` | enum | 第一版固定为 `demo` |
| `verified_at` | datetime | 绑定成功时间 |

演示环境由 A 预置“测试校园编号＋测试学号＋一次性绑定码”。接口只接受匹配且未绑定的测试身份，不能输入任意号码即认证成功；绑定码服务端保存摘要、使用后失效。不收集真实校园卡照片，不提供客户端自设认证结果的接口。

本人读取绑定结果时返回 `campus_id`、`student_no_masked`、`verification_mode`、`verified_at`；未绑定时 `data: null`。`student_no_masked` 只保留末四位，其余字符替换为 `*`。第一版不开放解绑或更换校园身份。

### 3.4 分类与地点字典（B，A/C 共用）

| 字典 | 字段 | 说明 |
|---|---|---|
| `Campus` | `id`, `name` | 校园/校区；即使只有一个，也保留该结构 |
| `Category` | `id`, `name`, `sort_order` | 物品类别，例如证件、电子产品、钥匙、书籍、衣物、其他 |
| `Location` | `id`, `campus_id`, `name`, `sort_order` | 位置，例如图书馆、教学楼、食堂、操场 |

字典使用固定初始化数据，第一版不提供字典管理页面。A 负责组织初始化流程，B 维护地点和分类的具体数据；三人共用同一份 ID，前端不可自己创建另一套枚举编号。已被使用的字典项不得删除或重新解释。

发布信息使用 `location_id`，服务端据此推导 `campus_id`，不让客户端提交相互矛盾的校区和地点。`location_detail` 用于补充“图书馆二楼”等文字。

### 3.5 失物/招领信息 `Post`（B）

| 字段 | API 类型 | 必填/默认 | 约束与含义 |
|---|---|---|---|
| `id` | string | 只读 | 信息 ID |
| `publisher_id` | string | 服务端生成 | 发布者 ID |
| `post_type` | enum | 必填 | `lost` / `found`，创建后不可修改 |
| `title` | string | 必填 | 2～60 字 |
| `category_id` | string | 必填 | 有效类别 ID |
| `description` | string | 必填 | 10～2000 字，物品特征和事件描述 |
| `location_id` | string | 必填 | 有效地点 ID |
| `campus_id` | string | 只读 | 由地点字典推导 |
| `location_detail` | string | 默认 `""` | 0～100 字，公开显示 |
| `occurred_at` | datetime | 必填 | 丢失或拾获时间；不能晚于服务端当前时间 |
| `handover_note` | string/null | 条件字段 | `found` 必填，1～200 字，保管或交接说明；`lost` 只能为空或不传，统一返回 `null` |
| `status` | enum | 默认 `open` | 服务端控制，见状态表 |
| `image_ids` | string[] | 请求默认 `[]` | 0～6 张；请求字段，响应改用 `images` |
| `created_at` | datetime | 只读 | 发布时间 |
| `updated_at` | datetime | 只读 | 最近更新时间 |
| `completed_at` | datetime/null | 默认 `null` | 完成时间，由业务流程设置 |

地点表示事件发生地点，不是住址。描述和图片应避免公开完整证件号码、私人地址或认领核验答案；认领证明通过私有申请提交。

第一版不增加草稿、审核、置顶、悬赏等状态。

#### 信息状态

| 值 | 中文含义 | 公开可见 | 允许编辑内容 | 允许新认领 |
|---|---|---|---|---|
| `open` | 进行中 | 是 | 仅发布者 | `lost`、`found` 均可，且申请者不是发布者 |
| `in_handover` | 交接中 | 是 | 否 | 否 |
| `completed` | 已完成 | 是 | 否 | 否 |
| `withdrawn` | 已撤回 | 否 | 仅发布者 | 否 |

`lost` 与 `found` 都可以进入 `in_handover`：`lost` 由捡到者的认领申请经失主同意后进入，`found` 由失主申请认领经发布者同意后进入。完成信息仍可公开查看并显示“已完成”，不再参与默认匹配。默认公开列表只展示 `open` 和 `in_handover`，可通过筛选查看 `completed`。

### 3.6 图片资源 `PostImage`（B）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 图片 ID |
| `owner_id` | string | 上传者，服务端内部字段 |
| `post_id` | string/null | 绑定的信息；未绑定时为 `null` |
| `url` | string | 响应中提供的受控图片地址，客户端不要自行拼接 |
| `mime_type` | string | `image/jpeg`、`image/png`、`image/webp` |
| `size_bytes` | integer | 实际大小，单张最多 5 MiB，即 5,242,880 字节 |
| `sort_order` | integer | 在信息内的顺序，由 `image_ids` 数组顺序决定 |
| `alt_text` | string | 图片的文字描述，5～100 字；发布或编辑时必填，供读屏朗读与图片无法显示时判断内容 |
| `created_at` | datetime | 上传时间 |

- 上传时校验实际文件内容，不只判断扩展名；拒绝无法解码的图片和 SVG 等未支持格式。
- 只能绑定本人上传的图片，一张图片只能绑定一条信息，`image_ids` 不允许重复。
- 编辑时 `image_ids` 缺省表示不改图片，传 `[]` 表示移除全部图片；指定数组表示整体替换和重新排序。
- 图片绑定及信息保存必须一起成功或失败；提交失败不能留下部分绑定。
- 未绑定图片仅上传者可访问，超过 24 小时可清理；撤回信息的图片仅发布者可访问。公开信息的图片可以匿名读取。
- 图片 URL 使用后端受控读取或等价方案，不能放在永久公开目录中绕过撤回权限；第一版图片响应使用 `Cache-Control: no-store`。撤回只能阻止后续读取，无法撤回别人已经保存的副本。
- 上传后返回的 `PostImageView` 字段为 `id`、`url`、`mime_type`、`size_bytes`、`sort_order`、`alt_text`；未绑定图片 `sort_order=0`。
- 每张图必须带一条 `alt_text`：5～100 字，描述图中物品的可辨识特征（颜色、品牌、损坏痕迹、特殊标记等），不得只写“图片”“照片”这类无信息量内容；上传接口校验长度，发布/编辑时校验非空。

### 3.7 认领申请 `Claim`（C）

| 字段 | API 类型 | 必填/默认 | 约束与含义 |
|---|---|---|---|
| `id` | string | 只读 | 申请 ID，同时作为沟通会话 ID |
| `post_id` | string | 必填 | 可关联 `lost` 或 `found` 信息，创建后不可修改 |
| `applicant_id` | string | 服务端生成 | 申请者，不能是信息发布者 |
| `verification_text` | string | 必填 | 10～1000 字，仅双方可见，例如未公开的物品细节 |
| `status` | enum | 默认 `pending` | 认领流程状态，与 `Post.status` 分开 |
| `decision_note` | string/null | 默认 `null` | 发布者同意或拒绝时的说明，最长 500 字；拒绝时必填 |
| `close_reason` | enum/null | 默认 `null` | 系统关闭原因，见下文 |
| `applicant_confirmed_at` | datetime/null | 默认 `null` | 申请者确认交接时间 |
| `publisher_confirmed_at` | datetime/null | 默认 `null` | 发布者确认交接时间 |
| `created_at` | datetime | 只读 | 申请时间 |
| `updated_at` | datetime | 只读 | 最近变更时间 |

目标为 `found` 时，申请者是自称失主的用户，审核者是招领发布者；目标为 `lost` 时，申请者是捡到物品的人，审核者是寻物发布者（失主）。两种目标的认领状态流转相同。

`Claim.status`：

| 值 | 含义 | 后续操作 |
|---|---|---|
| `pending` | 等待发布者核实 | 同意、拒绝、申请者取消；允许双方沟通 |
| `accepted` | 已同意，等待交接 | 双方分别确认；在双方均未确认前可取消；允许沟通 |
| `rejected` | 发布者拒绝 | 终态，只读 |
| `cancelled` | 申请者取消，或交接前任一方取消 | 终态，只读 |
| `completed` | 双方确认完成 | 终态，只读 |
| `closed` | 因信息撤回或其他申请被选中而关闭 | 终态，只读 |

`close_reason` 只在 `closed` 状态填写：`post_withdrawn`（信息撤回）、`another_claim_accepted`（已选择另一申请）。其他状态固定为 `null`。

同一用户对同一信息最多有一条 `pending` 或 `accepted` 申请；同一信息最多有一条 `accepted` 申请。历史申请保留，只有信息重新处于 `open` 且没有本人有效申请时，才可重新申请。

`verification_text` 创建后不允许直接改写；需要补充内容时通过会话发送，保留最初申请内容。

### 3.8 站内消息 `ClaimMessage`（C）

| 字段 | API 类型 | 约束与含义 |
|---|---|---|
| `id` | string | 消息 ID |
| `claim_id` | string | 所属认领申请 |
| `sender_id` | string | 从登录身份生成 |
| `content` | string | 1～1000 字纯文本 |
| `created_at` | datetime | 发送时间 |

第一版只支持文字，不支持附件、撤回消息、群聊、在线状态或任意用户私聊。消息只允许认领双方访问，不能因为信息本身公开就公开会话。

### 3.9 共用响应结构

| 结构 | 字段 |
|---|---|
| `UserSelf` | `id`, `username`, `nickname`, `bio`, `is_campus_verified`, `verification_mode`, `created_at`, `updated_at` |
| `UserSummary` | `id`, `nickname`, `is_campus_verified`, `verification_mode` |
| `PostSummary` | `id`, `post_type`, `title`, `category`（`id/name`）, `campus`（`id/name`）, `location`（`id/name`）, `occurred_at`, `status`, `cover_image`（`PostImageView` 或 null）, `publisher`（`UserSummary`）, `created_at`, `updated_at` |
| `PostDetail` | `PostSummary` 的全部字段，加 `description`, `location_detail`, `handover_note`, `images`（`PostImageView[]`）, `completed_at` |

`Post` 响应用 `publisher`、`category`、`campus`、`location` 对象返回摘要；关联 ID 从这些对象的 `id` 读取，不额外返回重复的 `publisher_id/category_id/campus_id/location_id`。写入请求仍使用字段表中规定的 `category_id/location_id`。

`ClaimView.post` 是提供给参与者的简短记录，即使信息撤回也保留；它不授予申请者读取撤回信息完整详情或图片的权限。

**【B 注记 · 开发期依赖】**
- `/users/me/posts` 需要登录身份。A 的登录接口未就绪时，用本地固定用户对象 stub（如 `request.user` 注入），联调时替换为真实身份。
- `/post-images/{id}/content` 返回二进制，用 Django `FileResponse` 实现，不要套 `code/message/data` 包装。
- `withdraw` 需要调用 C 的 `close_pending_claims`。C 未就绪时先留空实现（只改 `Post.status`），联调时补事务；接口返回结构不变。
- 仅发布招领（`post_type=found`）需要校园身份（`403 IDENTITY_REQUIRED`）；发布失物（`lost`）、编辑、上传图片只需登录。开发期可用预置 demo 用户通过校验，但接口在未绑定时仍必须返回 403，不要为方便开发放宽。
- 若 B 的 Django 侧用 DRF，统一响应用自定义 renderer 实现 `code/message/data` 包装，避免每个视图手写。

### 5.2 创建和修改字段

创建时接收 `post_type`、`title`、`category_id`、`description`、`location_id`、`location_detail`、`occurred_at`、`handover_note`、`image_ids`，必填性按 3.5 执行。

权限按 `post_type` 分路径：`lost` 只需登录即可创建；`found` 还要校验校园身份，未绑定返回 `403 IDENTITY_REQUIRED`，错误响应带可读提示（"非校园用户不能发布招领，请将物品送至失物招领处"），前端据此给出失物招领处地址与联系方式。可选字段 `request_id`（客户端生成的 UUID）用于幂等：同一发布者用相同 `request_id` 重复提交时返回首次创建的那条信息（201 或 200），不新建记录。

修改时接收以上字段但不接受 `post_type`；至少提交一个字段，依据修改后的完整对象校验。不能直接提交 `status`、发布者、完成时间或 `request_id`，状态通过专门的业务操作改变。

```json
{
  "post_type": "found",
  "title": "图书馆拾到一串钥匙",
  "category_id": "cat_keys",
  "description": "在图书馆二楼公共座位附近拾到一串钥匙，请失主说明具体特征。",
  "location_id": "loc_library",
  "location_detail": "二楼公共座位附近",
  "occurred_at": "2026-10-07T01:30:00Z",
  "handover_note": "暂由本人保管，核实后在校内约定地点交接。",
  "image_ids": ["img_501"]
}
```

示例中的分类、地点、图片 ID 都是假定已存在的数据；客户端实际值必须从字典和上传接口取得。

### 5.3 公开列表查询参数

| 参数 | 类型 | 默认/含义 |
|---|---|---|
| `post_type` | enum | 不传表示 `lost`、`found` 都查 |
| `keyword` | string | 0～50 字；对标题、描述做字面包含查询，不解释为正则或 SQL |
| `category_id` | string | 精确类别筛选 |
| `campus_id` | string | 校区筛选 |
| `location_id` | string | 地点筛选；若同时传校区，必须属于该校区，否则 400 |
| `status` | enum | 可传 `open/in_handover/completed`；不传查询 `open` 和 `in_handover`；不允许传 `withdrawn` |
| `occurred_from` | datetime | 事件时间下界，包含 |
| `occurred_to` | datetime | 事件时间上界，包含；下界不得大于上界 |
| `sort` | enum | `latest`（默认，发布时间降序）或 `occurred_latest`（事件时间降序）；最后均按 ID 降序打破平局 |
| `page` | integer | 默认 1 |
| `page_size` | integer | 默认 20，最大 100 |

所有有效筛选条件按 AND 组合，关键词的标题/描述命中按 OR 组合。空白关键词等同不筛选。未知字典 ID 返回 400。时间筛选按 `occurred_at`，列表默认排序按 `created_at`，不能混用。

### 5.4 状态操作约束

- `withdraw`：将 `open` 改为 `withdrawn`。若存在待处理认领，C 同步将全部 `pending` 关闭并填写 `post_withdrawn`；这两步必须在一个事务内完成。
- `restore`：将 `withdrawn` 改为 `open`，不恢复历史认领申请。
- `resolve`：仅供失物发布者表示“我已通过其他方式找回”，必须提交 `resolve_note`（5～200 字，说明怎么找回的），将 `lost/open` 改为 `completed`，记录操作人与完成时间；错标可通过 `reopen` 回退并留痕。招领信息不能通过这个接口绕过双方确认。
- `reopen`（新增）：发布者可将 `completed` 退回 `open`（误点“已找回”、交接后发现认错人）。仅当 C 不存在该信息的 `completed` 认领记录时允许；存在时返回 409，需先由 C 处理认领记录。
- `lost` 与 `found` 的交接中、完成状态都由 C 的认领业务驱动，见第 7 节；`resolve` 与 `reopen` 是发布者自己的状态操作，不涉及 C 的认领记录时可直接改。
- 重复执行已达到目标状态的同一操作返回当前对象和 200；若对象后来进入其他状态，则按当前状态判断并返回 409，不能倒退。
- 有待处理申请的招领信息仍允许发布者编辑，但不修改已提交的申请内容；进入交接中后禁止编辑。

## 6. C：认领、沟通和匹配接口

### 6.1 认领接口

| 方法 | 路径（均加 `/api/v1`） | 权限 | 请求/查询 | `data` 返回 |
|---|---|---|---|---|
| POST | `/claims` | 登录且认证，非发布者 | `post_id`, `verification_text` | `ClaimView`；201 |
| GET | `/claims/{id}` | 申请者或对应发布者 | 无 | `ClaimView` |
| GET | `/users/me/claims` | 登录 | `role`, `status`, `post_id`, `page`, `page_size` | 分页 `ClaimView` |
| POST | `/claims/{id}/accept` | 对应发布者 | 可选 `decision_note` | 修改后的 `ClaimView` |
| POST | `/claims/{id}/reject` | 对应发布者 | 必填 `decision_note`，1～500 字 | 修改后的 `ClaimView` |
| POST | `/claims/{id}/cancel` | 待审核仅申请者；交接前见 7.2 | 无 | 修改后的 `ClaimView` |
| POST | `/claims/{id}/confirm-handover` | 申请者或对应发布者 | 无；服务端识别确认方 | 修改后的 `ClaimView` |

`role` 默认 `applicant`（我申请的），还支持 `publisher`（我收到的）；一次只查一种。`status` 不传表示全部，可传第 3.7 节任一认领状态。`post_id` 仅在当前用户有权查看的申请集合内筛选，不能借筛选获取第三方记录；无记录时返回空分页。

创建申请必须同时满足：目标存在且公开、`post_type` 为 `lost` 或 `found`、`status=open`、申请者不是发布者、校园身份已绑定、没有本人有效重复申请。类型错误返回 400，非本人权限失败返回 403，信息不在可申请状态返回 409，有效申请重复返回 `409 DUPLICATE_RESOURCE`。

接口不接受 `publisher_id`、`applicant_id`、`status`、任何确认时间。

### 6.2 消息接口

| 方法 | 路径（均加 `/api/v1`） | 权限 | 请求/查询 | `data` 返回 |
|---|---|---|---|---|
| POST | `/claims/{id}/messages` | 认领双方，且申请为 `pending/accepted` | `content` | `MessageView`；201 |
| GET | `/claims/{id}/messages` | 认领双方，包含终态申请 | 可选 `after_id`, `limit` | `items: MessageView[]`, `next_after_id`, `has_more` |

读取规则：

1. 消息按会话内创建顺序正序返回，顺序由服务端保证。
2. 不传 `after_id` 从最早一条开始；传入后只返回该消息之后的内容。
3. `limit` 默认 50，范围 1～100。`after_id` 必须是本会话已有消息，否则 400。
4. `next_after_id` 为本批最后一条消息 ID；空批次时返回传入的 `after_id`，未传则为 `null`。有后续数据时 `has_more=true`。
5. 初次进入页面先读取全部历史批次，再每 5 秒查询后续消息；切换页面或退出登录时停止轮询。
6. 对非参与者返回 404；终态申请可看历史但不能发新消息，发送返回 409。
7. 客户端按消息 ID 去重。发送按钮在请求期间禁用；发送结果不明时先刷新消息列表，不自动重发。

第一版不单独建立通用会话表或未读数系统；每条申请自然对应一个双方会话。

### 6.3 匹配接口

| 方法 | 路径（均加 `/api/v1`） | 权限 | 请求/查询 | `data` 返回 |
|---|---|---|---|---|
| GET | `/posts/{id}/matches` | 登录，且是源信息发布者 | 可选 `limit`，默认 10，范围 1～20 | `source_post_id`, `items` |

此接口由 C 实现，虽然路径挂在 `posts` 下，B 不再重复实现。源信息必须为本人 `open` 信息，否则无权访问时返回 403（撤回等不公开资源对他人返回 404），本人非 `open` 时返回 409。

每个匹配项为：

```json
{
  "post": {
    "id": "2002",
    "post_type": "found",
    "title": "图书馆拾到一串钥匙",
    "category": {"id": "cat_keys", "name": "钥匙"},
    "campus": {"id": "campus_main", "name": "主校区"},
    "location": {"id": "loc_library", "name": "图书馆"},
    "occurred_at": "2026-10-07T01:30:00Z",
    "status": "open",
    "cover_image": null,
    "publisher": {
      "id": "1002",
      "nickname": "小周",
      "is_campus_verified": true,
      "verification_mode": "demo"
    },
    "created_at": "2026-10-07T02:00:00Z",
    "updated_at": "2026-10-07T02:00:00Z"
  },
  "score": 90,
  "reasons": ["category_same", "location_same", "time_near"]
}
```

`post` 使用完整 `PostSummary`。分数为 0～100 的规则分，**不是找到失主的概率**。

第一版统一规则：

- 候选必须是相反类型、同校区、同类别、`open`、非本人发布。
- 按两条信息中的角色识别丢失/拾获时间，要求 `found.occurred_at >= lost.occurred_at`，且间隔不超过 30 天；这是第一版简化规则，人工搜索仍可查其他记录。
- 同类别加 40 分；同 `location_id` 加 30 分；丢失到拾获间隔不超过 72 小时加 20 分。
- 标题经小写化、去除空白及标点后，存在共同的连续两个字符片段，加 10 分；任一标题处理后不足两字则此项为 0。此规则便于第一版实现，不能用于身份核实。
- `reasons` 按类别、地点、时间、关键词顺序，只返回实际加分项，对应 `category_same`、`location_same`、`time_near`、`keyword_overlap`。
- 按 `score DESC, created_at DESC, id DESC` 排序，取前 `limit` 条，无结果返回 `items: []`。
- 匹配即时计算、不落库，不使用私有认领证明或消息参与公开匹配。
- `lost` 发布者可以从匹配到的 `found` 信息发起认领；`found` 发布者查看匹配到的 `lost` 信息后，也可以对 `lost` 发起认领（作为拾获者），两条路径都进入同一个认领流程。

## 7. 三个子系统的状态协作

### 7.1 信息状态与认领状态转换

| 操作 | 操作前 | 操作后 | 执行责任 |
|---|---|---|---|
| 发布 | 无信息 | `Post=open` | B |
| 申请认领 | `found/open` 或 `lost/open` | 新增 `Claim=pending`，信息仍为 `open` | C |
| 拒绝申请 | `Claim=pending` | `Claim=rejected`，信息不变 | C |
| 取消待审核申请 | `Claim=pending` | `Claim=cancelled`，信息不变 | C |
| 同意某申请 | `found/open` 或 `lost/open`、目标申请 `pending` | 目标 `accepted`，信息 `in_handover`，其他待审核申请全部 `closed` | C 调 B，统一事务 |
| 第一方确认交接 | `Claim=accepted`、`Post=in_handover` | 只记录该方确认时间，两个状态不变 | C |
| 第二方确认交接 | 同上且另一方已确认 | `Claim=completed`、`Post=completed`，设置信息完成时间 | C 调 B，统一事务 |
| 交接前取消 | `Claim=accepted` 且双方都未确认 | `Claim=cancelled`、`Post=open`；其他已关闭申请不恢复 | C 调 B，统一事务 |
| 撤回信息 | `Post=open` | `Post=withdrawn`，其全部 `pending` 申请关闭 | B 调 C，统一事务 |
| 恢复信息 | `Post=withdrawn` | `Post=open`，历史申请不变 | B |
| 自行找回 | `lost/open` | `Post=completed` | B |
| 撤销完成 | `Post=completed` 且 C 无已完成认领 | `Post=open` | B；有已完成认领时先由 C 处理 |

### 7.2 必须共同遵守的规则

1. **一条招领信息只允许选择一名交接对象。** 同时同意两条申请时，最多一条成功，另一条返回 409。
2. 申请者不能审核自己的申请，发布者不能认领自己发布的信息。
3. 单方确认不是认领完成；只有两方都确认，才能同时完成申请和招领信息。
4. `accepted` 且双方都未确认时，任一方可以取消。只要已有一方确认，就不能直接取消、撤回或恢复；返回 409 并提示当前处于交接确认阶段。
5. 第一版不处理交接争议或确认撤销，这是未包含第四子系统的已知限制；联调验收使用双方正常确认的流程。
6. 同意、拒绝、取消等重复提交，在对应操作者仍有权限且当前已是相同目标状态时，返回当前对象；对象已进入不同状态时返回 409。重复确认不得覆盖第一次确认时间；已完成申请重复确认返回当前对象。
7. 创建认领不自动重试。同一用户同时创建两条有效申请，必须通过数据库约束或等价并发控制保证最多一条成功。
8. 招领信息完成后，不根据相似度自动完成任意寻物信息。失主如另发过寻物信息，由本人调用 `resolve` 标记找回，避免误关其他信息。
9. `completed` 撤销（`reopen`）只允许在 C 没有该信息的 `completed` 认领记录时进行；若认领已实际完成，撤销必须由 C 先处理认领记录，B 不得单方把信息改回 `open`。
10. 恢复信息、交接取消后的重新开放都不恢复历史申请；需要时重新申请。
11. 所有写操作必须在服务端检查当前状态，不能只依靠页面按钮隐藏。
12. 校外人员（`campus_verified=false`）发布的 `lost`，C 在认领与联系流程中提示申请者「对方为校外人员，建议在失物招领处交接」；该判断只读取 A 的身份状态，不改变 B 的信息状态，也不阻止认领。

### 7.3 内部业务接口及责任人

以下是后端模块之间的逻辑接口，**不是公开 HTTP 接口**。建议第一版在同一个后端应用和数据库中实现，使用同一数据库事务，不需要拆成三个服务。

| 提供方 | 建议函数/服务契约 | 调用方 | 返回/行为 |
|---|---|---|---|
| A | `require_user(token)` | B、C | 返回当前用户身份，含 `campus_verified`（是否已绑定校园身份）；无效时按 401 处理 |
| A | `require_campus_verified(user)` | B | 仅招领发布等需要校园身份的操作调用；不通过时按 403 `IDENTITY_REQUIRED` 处理 |
| A | `get_user_summaries(user_ids)` | B、C | 批量返回公开 `UserSummary`，包含 `campus_verified`，供 C 判断对方是否校外人员 |
| B | `get_post_for_claim(post_id, lock)` | C | 返回信息和发布者；`lock=true` 时加入当前事务的锁定读取 |
| B | `set_handover_state(post_id, transition)` | C | 只接受 `reserve/complete/reopen`，分别检查 `open→in_handover`、`in_handover→completed`、`in_handover→open`；`lost` 与 `found` 都接受 |
| B | `list_match_candidates(source_post)` | C | 返回符合公开可见性和候选硬条件的信息 |
| C | `close_pending_claims(post_id, reason, except_claim_id)` | B；C 自身 | 关闭待处理申请；`except_claim_id` 可为 null |
| C | `has_completed_claim(post_id)` | B | 返回该信息是否存在 `completed` 认领记录，供 `reopen` 前校验 |

事务由发起业务操作的上层服务负责：

- 同意申请：C 开始事务 → 锁定信息 → 锁定该信息相关申请 → 检查当前状态 → 接受目标申请、关闭竞争申请 → 调用 B 将信息设为交接中 → 一起提交。
- 双方确认：C 在同一事务内锁定信息和申请 → 记录当前用户的确认 → 两人均确认时调用 B 完成信息 → 一起提交。
- 撤回信息：B 开始事务 → 锁定信息及相关申请 → 校验仍为 `open` → 撤回并调用 C 关闭待处理申请 → 一起提交。
- 新申请、取消、消息发送及信息编辑也必须按需要检查同一套状态；状态检查和写入之间不能让并发操作破坏规则。
- 统一锁定顺序：先信息，再该信息的申请（按 ID 升序），最后消息等从属记录；所有涉及这些对象的写入均遵守，降低互相等待的风险。
- 被调用的内部函数不得自行提前提交事务。任一步失败，前面的状态变化必须回滚。

前端不能先请求“申请完成”，再另外请求“信息完成”。这种做法会产生只成功一半的状态。

## 8. 三人联调顺序和共同验收

### 8.1 实施顺序

1. **先确定基础契约**：三人确认本文件的字段、ID 类型、响应包装、状态和路径。A 建立统一登录和错误处理；B 提供分类、校区、地点测试字典。
2. **独立开发**：A 实现用户接口；B 用约定身份对象开发发布浏览；C 用约定信息对象开发认领和消息。模拟数据必须遵守相同结构。
3. **打通身份和信息**：注册 → 登录 → 演示校园身份绑定 → 上传图片 → 发布 → 列表和详情 → 编辑。
4. **打通认领主流程**：另一用户申请 → 发布者查看并沟通 → 同意 → 双方确认 → 信息与申请同时完成。
5. **补齐分支**：拒绝、取消、撤回恢复、多申请竞争、匹配、无权限访问。

### 8.2 建议测试数据

准备三名普通测试用户，无需管理员账号：

| 用户 | 用途 |

| 编号 | 场景 | 预期 | 负责人 |
|---|---|---|---|
| T01 | 未登录发布；登录但未认证发布 | 分别 401、403；数据库不产生信息 | A+B |

## 9. 协作时的修改规则

- 字段、枚举、响应结构、权限或路径发生变化时，先修改本文件，并通知另外两人再改实现。
- 业务接口按子系统归属维护，禁止两个人各做一份“我的发布”或“认领完成”逻辑。
- 数据表结构修改由对应负责人提供迁移；涉及共享字段时先共同确认，不手动修改其他人的本地数据库。
- B 和 C 对状态协作一起验收；成员个人报告分别说明自己实现的部分，共同联调列为合作成果。
- 未决定的实现细节（语言、框架、数据库、页面样式）不改变本契约；若技术选择无法支持上述事务规则，应先调整设计再实现。

**确认这份草案后，A 可以从用户与身份接口开始，B 从字典和发布接口开始，C 从认领状态机和内部接口开始。**
